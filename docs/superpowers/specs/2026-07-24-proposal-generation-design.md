# Proposal Generation on Apply — Design

## Purpose

Wire up the "Apply" button on the job scanner detail page's job list to
actually generate a proposal via AI — cover letter, screening question
answers, and a recommended attachment subset — instead of just flipping
`apply_status`. Supersedes the "generated by the scan pipeline, not created
here" and "no regenerate" notes in `2026-07-15-proposals-page-design.md`:
proposals are now created and (re)generated from this app.

## Flow

1. User clicks **Apply** on a job row in `job-list.tsx`.
2. Client checks the job's scan config has `proposal_template_id` set. If not:
   `toast.error("Set a proposal template on this scanner first")`, abort — no
   row created, `apply_status` untouched.
3. Otherwise, call `POST /api/proposals/apply` with `{ jobId }`. Server:
   - Loads the job (`upwork_jobs`) and its `user_scan_config`
     (`proposal_template_id`, `attachments`).
   - Re-checks `proposal_template_id` server-side (400 if missing — same
     guard, don't trust client).
   - Inserts a `proposals` row: `user_id`, `upwork_job_id`, `attachment: []`
     (filled in by generation, not here).
   - Updates `upwork_jobs.apply_status = 'Applied'`.
   - Returns `{ proposalId }`.
4. Client `router.push(\`/proposals/${proposalId}\`)`.
5. `/proposals/[id]` detail page: if `cover_letter_generated IS NULL`, show a
   loading state and auto-fire `POST /api/ai/generate-proposal { proposalId }`
   on mount. Once it returns, render normally (existing `ProposalDetail`
   layout, no changes needed there — it already renders `cover_letter_generated`,
   `question_answer`, `attachments`).
   - "Regenerate" button (new, next to the Cover Letter card) re-fires the same
     endpoint any time — not just when null.

## `POST /api/ai/generate-proposal`

Input: `{ proposalId }`. Auth required (matches `generate-test` pattern).

Loads:
- `proposals` row by id (RLS scopes to owner).
- Joined `upwork_jobs`: `title`, `description`, `screening_questions`,
  `scan_config_id`.
- `user_scan_config` by `scan_config_id`: `proposal_template_id`,
  `question_instruction`, `question_answer_base`, `attachments` (candidate
  attachment ids).
- `proposal_templates` by `proposal_template_id`: `template`, `ai_instruction`.
- `attachments` rows `.in("id", config.attachments)`: `id`, `file_name`,
  `description` (candidate pool for AI pick).
- `user_profiles` row for `user_scan_config.user_id` (the freelancer who owns
  the scan — not `upwork_jobs.user_id`, which is nullable): `summary`,
  `current_role`, `previous_experience`, `skills_text`, `portfolio`,
  `key_proof_points`, `positioning_notes`.

404/400 if template or job missing.

One `sumopod` chat-completions call, JSON-mode, single system prompt covering
all three outputs to keep it one round trip:

- **Cover letter**: same contract as `generate-test`'s "cover" kind —
  rewrite `template`, filling `[prompt]…[/prompt]` sections, keep the rest
  verbatim — but the prompt also includes the profile fields above as the
  freelancer's real background (not just template + job like `generate-test`
  does today), so filled sections speak from actual experience/skills.
- **Question answers**: if `screening_questions` is non-empty, produce
  `{question, answer}[]` — one tailored answer per question, sourced from
  `question_answer_base` + `question_instruction`, same intent as
  `generate-test`'s "question" kind. Empty array if no screening questions.
- **Attachment picks**: given the candidate list (`file_name` + `description`)
  and job title/description, return an array of candidate `id`s worth
  attaching — only genuinely relevant ones, can be empty. Candidates not in
  the returned array are simply not attached.

Response JSON shape:
```json
{ "coverLetter": string, "questionAnswers": [{ "question": string, "answer": string }], "attachmentIds": string[] }
```

Server validates `attachmentIds` are a subset of the candidate ids (drop
anything the model hallucinates), then updates the `proposals` row:
`cover_letter_generated`, `question_answer`, `attachment` (validated id
array), `last_generated_at: now()`, `total_token_used` (from the completion
response usage field).

Returns the updated proposal fields so the client can render without a
refetch.

## Out of scope

- `client_paint` (AI pain-point summary column) — not used by the UI today,
  not requested, left null.
- Attachment picker / manual override UI — AI's pick is final; user can only
  see the result, not adjust it (matches "no edit-before-send" decision).
- Any change to the Dismiss button or non-Apply tabs in `job-list.tsx`.
- Retrying/queueing generation failures beyond a toast + leaving
  `cover_letter_generated` null so "Regenerate" can be used.
